## 1. Product overview

### 1.1 Product vision

CaseVerse is an AI-powered mystery-generation and investigation web
application. A user submits a short scenario, premise, or story idea.
The backend uses Google Gemini to turn that input into a fictional,
self-contained mystery challenge with:

-   A defined crime or central mystery.
-   A coherent cast of suspects, each with a motive, opportunity, and
    background.
-   One canonical culprit and a logically consistent explanation.
-   A collection of fictional evidence artifacts generated by AI, such
    as chat conversations, witness statements, photographs or image
    descriptions, CCTV/transcript records, timelines, and documents.
-   Optional hints that help a player progress without immediately
    revealing the solution.

The player examines the evidence, compares statements, identifies
contradictions, requests hints when needed, and submits one suspect as
the culprit. The application evaluates the answer and presents the final
explanation, including how the evidence supports the solution.

CaseVerse is a fictional entertainment experience. It is not a
real-world law-enforcement, forensic, or evidentiary tool.

### 1.2 Product objective

Deliver a polished, responsive, end-to-end web application that
demonstrates the complete journey:

1.  User creates a mystery from a short scenario.
2.  Backend generates and validates a complete mystery using Gemini.
3.  User opens the generated case.
4.  User investigates suspects and evidence artifacts.
5.  User requests progressive hints.
6.  User submits a culprit.
7.  Application reveals whether the answer is correct and explains the
    solution.
8.  User can review completed cases and their outcomes.

### 1.3 Primary user

A person who enjoys detective stories, puzzles, escape-room experiences,
and interactive mystery games. The primary experience should be
approachable without requiring specialist knowledge.

### 1.4 Product principles

-   **Fairness:** The culprit must be deducible from the evidence
    provided.
-   **Consistency:** Evidence, suspect profiles, timeline, hints, and
    solution must agree.
-   **No premature spoilers:** The culprit and solution remain hidden
    until the player submits an answer or explicitly reveals the
    solution.
-   **Evidence-led play:** The solution explanation must reference
    specific evidence artifacts.
-   **Fictional by design:** All generated people, events,
    organizations, messages, and evidence are fictional.
-   **Transparent AI behavior:** Clearly indicate that case content is
    AI-generated.
-   **Resilience:** A failed or malformed AI response must not create a
    broken or unsolvable case.

## 2. Scope

### 2.1 MVP --- must have

1.  Landing page explaining CaseVerse.
2.  User registration, login, logout, and authenticated session
    handling.
3.  Create-case form with a short scenario prompt and optional
    generation preferences.
4.  Gemini-powered mystery generation on the server.
5.  Server-side validation of the generated mystery before it becomes
    playable.
6.  Case library showing a user's created cases and investigation
    status.
7.  Case briefing screen.
8.  Suspect directory and individual suspect profiles.
9.  Evidence room with categorized, readable evidence artifacts.
10. Evidence detail view or modal.
11. Investigation board/list where the player can review and organize
    evidence. MVP can use a simple evidence collection and notes
    experience; visual drag-and-drop connections are not required.
12. Progressive hint requests with a limited hint sequence.
13. Culprit selection and answer submission.
14. Result screen with correct/incorrect outcome and evidence-backed
    solution reveal.
15. Case completion state and investigation history.
16. Responsive desktop and mobile layouts.
17. Loading, empty, error, retry, and generation-in-progress states.
18. Basic automated tests for critical business logic and API behavior.

### 2.2 Explicitly out of scope for MVP

Do not implement these unless separately approved and added to this
specification:

-   Multiplayer, co-op, live rooms, or competitive leaderboards.
-   Real-time chat between players.
-   User-created public marketplace or community case sharing.
-   Payments, subscriptions, credits, or in-app purchases.
-   Voice acting, generated audio, or playable CCTV video.
-   Real video generation. CCTV should initially be represented as a
    fictional transcript, timestamp log, or text-based recording report.
-   Real WhatsApp integration. Chat evidence is a fictional chat
    transcript styled like a messaging artifact.
-   Real-world facial recognition, identity matching, or forensic
    analysis.
-   Uploading real people's private messages, CCTV, or sensitive
    personal data.
-   Public user profiles or social following.
-   Native mobile applications.
-   Admin console beyond basic operational logging.
-   Fine-tuning or training a custom AI model.

### 2.3 Future-ready, not MVP requirements

Keep the architecture reasonably extensible for future image generation,
richer media artifacts, public case sharing, multiplayer, difficulty
levels, and additional mystery genres. Do not build these features
pre-emptively.

## 3. User journeys

### 3.1 Create a mystery

1.  Visitor opens the CaseVerse landing page.
2.  User registers or logs in.
3.  User selects **Create a Mystery**.
4.  User enters a scenario or premise in their own words.
5.  User optionally selects genre, difficulty, and desired case length.
6.  User submits the form.
7.  UI displays a generation state and prevents duplicate submissions.
8.  Frontend sends the request to the backend.
9.  Backend validates input, creates a generation job/case record, and
    calls Gemini.
10. Backend parses and validates Gemini's structured output.
11. If valid, backend stores the complete case and marks it `ready`.
12. User is redirected to the case briefing page.
13. If generation fails, the case is marked `failed`, the user sees a
    useful error and can retry. Do not expose API keys, raw provider
    errors, or internal prompts.

### 3.2 Investigate a mystery

1.  User opens a ready case.
2.  User reads the case briefing and objective.
3.  User reviews the suspect list.
4.  User opens suspect profiles and compares their statements, motives,
    and alibis.
5.  User browses evidence by category.
6.  User opens individual evidence artifacts.
7.  User can save investigation notes and mark evidence as reviewed.
8.  User can request the next available hint.
9.  User selects a suspect as the culprit and submits a final
    accusation.
10. Backend evaluates the answer against the canonical culprit stored in
    the case.
11. User sees the result and the evidence-backed explanation.
12. Case is marked completed and appears in history.

### 3.3 Resume a case

1.  User opens their case library.
2.  In-progress cases are visually distinguished from completed cases.
3.  User opens an in-progress case.
4.  Previously reviewed evidence, notes, hint usage, and progress are
    restored.
5.  User continues the investigation.

### 3.4 Reveal solution

The player may reveal the solution without submitting an accusation only
if the product deliberately exposes a **Reveal Solution** action. If
included in MVP, show a confirmation warning and record the case as
`revealed` rather than `solved`. Do not treat a revealed answer as a
correct solve.

## 4. Functional requirements

Priority definitions: **P0** = release blocker; **P1** = important MVP
feature; **P2** = optional polish.

### 4.1 Authentication and account

-   **AUTH-01 (P0):** Users can register with name, email, and password.
-   **AUTH-02 (P0):** Users can log in and log out.
-   **AUTH-03 (P0):** Passwords are hashed using a suitable
    password-hashing library; never store plaintext passwords.
-   **AUTH-04 (P0):** Protected APIs require valid authentication.
-   **AUTH-05 (P0):** A user can only read or modify their own cases and
    progress.
-   **AUTH-06 (P1):** Persist authentication securely. Prefer HTTP-only,
    secure, same-site cookies for JWT/session tokens in production. Do
    not store long-lived authentication tokens in localStorage.
-   **AUTH-07 (P1):** Validate and normalize email addresses; enforce
    unique email addresses.

### 4.2 Mystery creation

-   **GEN-01 (P0):** Accept a scenario prompt between 50 and 2,000
    characters. Show the character count.
-   **GEN-02 (P0):** Optional genre: `murder`, `theft`, `disappearance`,
    `espionage`, `sabotage`, `other`.
-   **GEN-03 (P0):** Optional difficulty: `easy`, `medium`, `hard`;
    default `medium`.
-   **GEN-04 (P0):** Optional case length: `short`, `standard`,
    `extended`; default `standard`.
-   **GEN-05 (P0):** Generate a complete mystery with 3--6 suspects.
-   **GEN-06 (P0):** Generate 5--10 evidence artifacts for a standard
    case. Short cases may contain 4--6; extended cases may contain
    8--12.
-   **GEN-07 (P0):** Generate exactly one canonical culprit.
-   **GEN-08 (P0):** Generate at least 2 meaningful clues that support
    the correct solution and at least 1 red herring that is explainable
    and does not make the case unfair.
-   **GEN-09 (P0):** The mystery must have a coherent event timeline and
    a solution supported by evidence.
-   **GEN-10 (P0):** Store the canonical solution separately from
    player-visible case content.
-   **GEN-11 (P0):** Validate the AI output against a strict schema and
    semantic consistency rules.
-   **GEN-12 (P0):** Do not publish a case until generation and
    validation succeed.
-   **GEN-13 (P1):** Allow a user to retry a failed generation.
-   **GEN-14 (P1):** Prevent duplicate case creation when a client
    retries the same request; use an idempotency key or equivalent
    request protection.

### 4.3 Investigation experience

-   **CASE-01 (P0):** Show title, synopsis, setting, incident summary,
    objectives, and difficulty in the case briefing.
-   **CASE-02 (P0):** Show all suspects with name, role/relationship,
    short description, and portrait placeholder or generated avatar.
-   **CASE-03 (P0):** Show suspect profiles with motive, known
    relationship to the incident, statement, and alibi. Do not reveal
    hidden guilt or the canonical culprit.
-   **CASE-04 (P0):** Show evidence artifacts in a searchable/filterable
    evidence room.
-   **CASE-05 (P0):** Evidence categories include `chat`, `document`,
    `witness_statement`, `cctv_log`, `photo`, `timeline`, and `other`.
-   **CASE-06 (P0):** Each evidence artifact has a title,
    description/content, source, timestamp or relevant time where
    applicable, and a category.
-   **CASE-07 (P0):** Chat artifacts are fictional transcripts with
    sender, message, and timestamp fields.
-   **CASE-08 (P0):** CCTV artifacts are fictional text logs or
    transcripts, not actual recordings in MVP.
-   **CASE-09 (P0):** Photo artifacts must include a textual visual
    description and may use a neutral placeholder image in MVP. Do not
    imply a real image was generated when it was not.
-   **CASE-10 (P1):** Players can mark evidence as reviewed.
-   **CASE-11 (P1):** Players can write and save private case notes.
-   **CASE-12 (P1):** Preserve progress across refreshes and sessions.
-   **CASE-13 (P1):** Show a progress indicator based on evidence
    reviewed, hints used, and whether an accusation has been submitted.
    Do not equate opening every artifact with understanding the mystery.

### 4.4 Hints

-   **HINT-01 (P0):** Each case has a sequence of 3 progressive hints.
-   **HINT-02 (P0):** Hint 1 nudges the player toward an important area
    of investigation without naming the culprit.
-   **HINT-03 (P0):** Hint 2 connects two or more pieces of evidence.
-   **HINT-04 (P0):** Hint 3 gives a strong deduction cue but does not
    directly state the answer.
-   **HINT-05 (P0):** Hints must not contradict the case evidence or
    solution.
-   **HINT-06 (P0):** A user can request only the next hint in sequence.
    Previously revealed hints remain available.
-   **HINT-07 (P0):** Hint use is persisted and visible to the player.
-   **HINT-08 (P1):** Hint requests should be served from stored
    generated hints, not trigger a fresh Gemini call each time.

### 4.5 Accusation and result

-   **SOLVE-01 (P0):** User selects one suspect and submits an
    accusation.
-   **SOLVE-02 (P0):** Backend validates that the selected suspect
    belongs to the case.
-   **SOLVE-03 (P0):** Backend evaluates the accusation against the
    canonical culprit ID. Never trust a client-provided answer key.
-   **SOLVE-04 (P0):** Show correct or incorrect outcome.
-   **SOLVE-05 (P0):** Reveal the canonical solution after the first
    final accusation, whether correct or incorrect.
-   **SOLVE-06 (P0):** Explanation must identify the culprit, motive,
    method, opportunity, and a step-by-step chain of evidence.
-   **SOLVE-07 (P0):** Each key deduction in the solution must reference
    one or more evidence artifact IDs.
-   **SOLVE-08 (P0):** Record submitted suspect, correctness, timestamp,
    and hints used.
-   **SOLVE-09 (P1):** A completed case cannot be re-accused unless a
    future replay feature is added.
-   **SOLVE-10 (P1):** Distinguish `solved`, `incorrect`, and `revealed`
    completion outcomes.

### 4.6 Case library

-   **LIB-01 (P0):** Show cases created by the authenticated user.
-   **LIB-02 (P0):** Display title, genre, difficulty, creation date,
    and status.
-   **LIB-03 (P0):** Support filtering by status: `generating`, `ready`,
    `in_progress`, `completed`, `failed`.
-   **LIB-04 (P0):** Allow opening ready and in-progress cases.
-   **LIB-05 (P1):** Allow deleting a user's own case with confirmation.
    Deletion must also remove associated progress records.
-   **LIB-06 (P1):** Provide useful empty states and a clear create-case
    action.

## 5. AI and Gemini integration

### 5.1 Provider and server boundary

-   AI provider: **Google Gemini**.
-   All Gemini requests must originate from the backend.
-   Never expose the Gemini API key or privileged model configuration to
    the browser.
-   Read the API key from environment configuration.
-   Use the official Google GenAI SDK supported by the selected backend
    runtime.
-   Keep model name configurable through `GEMINI_MODEL`.
-   Use structured JSON output/schema constraints where supported by the
    chosen Gemini model and SDK.
-   Treat all model output as untrusted input until parsed and
    validated.

### 5.2 Generation contract

The generation prompt must instruct Gemini to create a fictional,
fair-play mystery based on the user's scenario, and return structured
data matching the schema in Section 6.

The generation prompt must explicitly require:

1.  Exactly one culprit selected from the generated suspects.
2.  A complete private solution and reasoning chain.
3.  A timeline that is consistent with all statements and artifacts.
4.  Evidence that permits a careful player to deduce the culprit.
5.  Suspects with plausible motives and credible alibis or statements.
6.  At least one red herring that can be logically explained.
7.  No clue that directly identifies the culprit too early unless
    appropriate for the selected difficulty.
8.  No contradictions unless the contradiction is intentional and
    explainable.
9.  Evidence-backed deductions with valid evidence IDs.
10. Entirely fictional names, organizations, messages, locations, and
    events.

### 5.3 Generation and validation pipeline

Implement this pipeline on the server:

1.  Validate and normalize user input.
2.  Create a case record with `status=generating`.
3.  Build a prompt from the user scenario and selected preferences.
4.  Call Gemini with a bounded timeout and token/output limits.
5.  Parse the response as JSON.
6.  Validate structure with a runtime schema validator (for example,
    Zod).
7.  Validate semantic invariants:
    -   3--6 unique suspects.
    -   Exactly one culprit ID and it references an existing suspect.
    -   Evidence count is within the selected case-length range.
    -   All evidence IDs are unique.
    -   All evidence references in the solution exist.
    -   All suspect IDs referenced by evidence exist.
    -   Exactly 3 hints exist and are ordered.
    -   Timeline entries are parseable and chronologically coherent.
    -   The solution contains a clear motive, method, opportunity, and
        deduction chain.
    -   The correct culprit is not disclosed in public-facing
        descriptions or evidence metadata.
8.  If validation fails, perform at most one controlled
    repair/regeneration attempt using validation errors. Do not loop
    indefinitely.
9.  If still invalid, mark the case `failed`, log a sanitized error, and
    allow retry.
10. If valid, persist public content and private solution separately,
    then mark the case `ready`.

### 5.4 AI output quality

A generated case is not acceptable merely because it is valid JSON. It
must be playable and fair.

The backend should run deterministic checks. Additionally, include a
second AI review pass only if it fits latency and budget constraints.
The review pass should assess solvability, evidence sufficiency,
contradiction quality, and spoiler leakage. If the review fails, allow
one repair attempt. Do not make runtime correctness depend solely on a
second model call.

### 5.5 AI reliability and cost controls

-   Configure request timeout and maximum output tokens.
-   Limit prompt length and scenario length.
-   Apply per-user generation rate limits.
-   Prevent repeated generation requests from creating uncontrolled
    provider costs.
-   Do not retry provider errors indefinitely.
-   Distinguish provider/network errors, invalid model output, and
    application validation failures in server logs.
-   Do not return raw provider error payloads to the client.
-   Record model name and generation timestamp for debugging.
-   Avoid logging full private solution content or sensitive user input
    unnecessarily.

### 5.6 Fictional media policy

For MVP, Gemini generates the content and descriptions of artifacts, not
necessarily binary media files.

-   WhatsApp-style artifact: render a fictional chat transcript in a
    chat-bubble interface. Clearly label it as fictional case evidence.
-   CCTV artifact: render a fictional camera log or transcript with
    camera ID and timestamps. Do not show a fake video player.
-   Photo artifact: show an image placeholder with an AI-generated
    visual description. If image generation is later integrated, store
    the asset URL and provider metadata separately.
-   Document artifact: render a readable document/evidence card.
-   Witness statement: render the witness's fictional statement and
    metadata.

Never connect to a real WhatsApp account, CCTV system, camera, or
private data source for this MVP.

## 6. Canonical data contracts

Use these contracts as the source for frontend types, backend validation
schemas, database models, and API responses. Exact implementation types
may differ by layer, but field meaning and visibility rules must remain
consistent.

### 6.1 Mystery generation output

``` ts
type Difficulty = "easy" | "medium" | "hard";
type CaseLength = "short" | "standard" | "extended";
type Genre =
  | "murder"
  | "theft"
  | "disappearance"
  | "espionage"
  | "sabotage"
  | "other";

type EvidenceType =
  | "chat"
  | "document"
  | "witness_statement"
  | "cctv_log"
  | "photo"
  | "timeline"
  | "other";

interface GeneratedMystery {
  title: string;
  genre: Genre;
  difficulty: Difficulty;
  setting: string;
  synopsis: string;
  incident: {
    summary: string;
    occurredAt: string; // ISO-8601 timestamp or documented fictional relative time
    location: string;
  };
  objective: string;
  suspects: Suspect[];
  evidence: Evidence[];
  timeline: TimelineEvent[];
  hints: Hint[];
  solution: PrivateSolution;
}

interface Suspect {
  id: string; // stable case-local ID, e.g. suspect_01
  name: string;
  role: string;
  relationshipToIncident: string;
  description: string;
  motive: string; // player-visible but must not disclose actual guilt
  statement: string;
  alibi: string;
}

interface Evidence {
  id: string; // stable case-local ID, e.g. evidence_01
  type: EvidenceType;
  title: string;
  summary: string;
  source: string;
  createdAt?: string;
  relevantTime?: string;
  content: EvidenceContent;
  relatedSuspectIds: string[];
  importance: "key" | "supporting" | "red_herring";
}

type EvidenceContent =
  | { kind: "chat"; participants: string[]; messages: Array<{
      sender: string; message: string; timestamp: string;
    }> }
  | { kind: "document"; body: string; documentDate?: string }
  | { kind: "witness_statement"; witnessName: string; statement: string; recordedAt?: string }
  | { kind: "cctv_log"; cameraId: string; entries: Array<{
      timestamp: string; description: string;
    }> }
  | { kind: "photo"; visualDescription: string; capturedAt?: string; location?: string }
  | { kind: "timeline"; events: Array<{
      timestamp: string; description: string;
    }> }
  | { kind: "other"; body: string };

interface TimelineEvent {
  id: string;
  timestamp: string;
  description: string;
  relatedEvidenceIds: string[];
  relatedSuspectIds: string[];
}

interface Hint {
  order: 1 | 2 | 3;
  text: string;
}

interface PrivateSolution {
  culpritSuspectId: string;
  motive: string;
  method: string;
  opportunity: string;
  summary: string;
  reasoningSteps: Array<{
    explanation: string;
    supportingEvidenceIds: string[];
    eliminatesSuspectIds?: string[];
  }>;
  redHerringExplanation: string;
}
```

**Important visibility rule:** `PrivateSolution` is server-only until
the user has submitted a final accusation or explicitly revealed the
solution. The public case API must never include `culpritSuspectId`,
private solution fields, hidden AI review notes, or any equivalent
answer-key field before that point.

### 6.2 Database entities

Use MongoDB with Mongoose (or a comparably mature MongoDB ODM).
Suggested collections:

**User** - `_id` - `name` - `email` (unique, normalized) -
`passwordHash` - `createdAt` - `updatedAt`

**Case** - `_id` - `ownerId` (User reference, indexed) - `title` -
`scenarioPrompt` - `genre` - `difficulty` - `caseLength` - `status`:
`generating | ready | in_progress | completed | failed` -
`publicContent`: synopsis, incident, objective, suspects, evidence,
timeline, hints - `privateSolution`: canonical solution; never returned
by ordinary case endpoints - `generation`: model, promptVersion,
generatedAt, retryCount, sanitizedFailureCode - `createdAt` -
`updatedAt`

**InvestigationProgress** - `_id` - `caseId` (unique with `userId`) -
`userId` - `reviewedEvidenceIds: string[]` - `notes: string` -
`revealedHintOrders: number[]` - `status`:
`not_started | in_progress | solved | incorrect | revealed` -
`accusedSuspectId?: string` - `isCorrect?: boolean` -
`submittedAt?: Date` - `completedAt?: Date` - `createdAt` - `updatedAt`

For the MVP, the case creator is also the investigator. If cases later
become shareable, progress must remain user-specific and separate from
the Case document.

### 6.3 Data security rules

-   Never send `privateSolution` in a case list, case detail, suspect,
    evidence, hint, or progress response.
-   Only the answer-submission/reveal endpoint may return the solution,
    and only after the required action.
-   Enforce owner checks in every case and progress operation.
-   Validate ObjectIds and case-local IDs.
-   Do not accept owner IDs from the client as authority; derive the
    authenticated user ID from the session.
-   Avoid mass assignment: explicitly map permitted request fields.
-   Do not store passwords, Gemini keys, or session secrets in case
    documents.
-   Use database indexes for owner/status queries and unique progress
    per user/case.

-   **Frontend build tool:** Vite

    tests.
-   **Deployment:** Frontend and backend may be deployed separately. Use

### 7.2 High-level architecture

``` text
Browser (React + TypeScript + Vite)
          |
          | HTTPS / REST JSON
          v
Node.js + Express API
  |       |          |
  |       |          +--> Auth/session middleware
  |       +-------------> Case / progress services
  +---------------------> Gemini service
  |
  v
MongoDB (Users, Cases, InvestigationProgress)

```

### 7.3 Architectural boundaries

-   React handles presentation, navigation, and user interaction.
-   Express routes handle HTTP concerns, authentication, validation, and
    response formatting.
-   Controllers coordinate requests but should not contain complex
    business logic.
-   Services own case generation, case validation, hint progression, and
    accusation evaluation.
-   Models define persistence.
-   Gemini integration is isolated behind a service module so the
    provider can be changed later without rewriting routes.
-   Shared types/schemas should be reused where practical, but backend
    validation remains authoritative.
-   Do not call Gemini directly from React.

## 8. REST API contract

Base path: `/api/v1`

All successful responses should use a consistent JSON envelope.
Suggested format:

``` json
{
  "success": true,
  "data": {},
  "message": "Optional human-readable message"
}
```

Errors:

``` json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request could not be processed.",
    "details": []
  }
}
```

Do not expose stack traces, secrets, prompts, raw Gemini responses, or
private solution data in error responses.

### 8.1 Authentication

  Method   Endpoint           Purpose          Auth
  -------- ------------------ ---------------- ------
  POST     `/auth/register`   Create account   No
  POST     `/auth/login`      Start session    No
  POST     `/auth/logout`     End session      Yes
  GET      `/auth/me`         Current user     Yes

### 8.2 Cases

  ------------------------------------------------------------------------------------------
  Method            Endpoint                            Purpose            Auth
  ----------------- ----------------------------------- ------------------ -----------------
  POST              `/cases`                            Start mystery      Yes
                                                        generation

  GET               `/cases`                            List current       Yes
                                                        user's cases

  GET               `/cases/:caseId`                    Get public case    Yes
                                                        briefing/content

  DELETE            `/cases/:caseId`                    Delete own case    Yes

  POST              `/cases/:caseId/retry-generation`   Retry a failed     Yes
                                                        generation
  ------------------------------------------------------------------------------------------

`POST /cases` request:

``` json
{
  "scenario": "A short fictional premise supplied by the user...",
  "genre": "murder",
  "difficulty": "medium",
  "caseLength": "standard"
}
```

Generation may be synchronous for the first implementation if it
reliably completes within hosting limits. Prefer a job/polling pattern
if generation can take longer:

-   `POST /cases` returns `202 Accepted` with
    `{ "caseId": "...", "status": "generating" }`.
-   Client polls `GET /cases/:caseId` or a dedicated status endpoint.
-   Once ready, response includes public case content only.

Do not make the UI assume generation is instant.

### 8.3 Investigation progress

  ---------------------------------------------------------------------------------
  Method            Endpoint                    Purpose           Auth
  ----------------- --------------------------- ----------------- -----------------
  GET               `/cases/:caseId/progress`   Get current       Yes
                                                user's progress

  PATCH             `/cases/:caseId/progress`   Save reviewed     Yes
                                                evidence and
                                                notes

  POST              `/cases/:caseId/hints`      Reveal next hint  Yes
  ---------------------------------------------------------------------------------

Example progress update:

``` json
{
  "reviewedEvidenceIds": ["evidence_01", "evidence_03"],
  "notes": "The timestamps in the chat and camera log do not match."
}
```

The server must validate all evidence IDs against the case and must not
allow clients to modify hint count, completion status, or answer fields
through this endpoint.

### 8.4 Solve and reveal

  ----------------------------------------------------------------------------------------
  Method            Endpoint                           Purpose           Auth
  ----------------- ---------------------------------- ----------------- -----------------
  POST              `/cases/:caseId/accusations`       Submit final      Yes
                                                       suspect selection

  POST              `/cases/:caseId/reveal-solution`   Explicitly reveal Yes
                                                       solution, if
                                                       enabled
  ----------------------------------------------------------------------------------------

Accusation request:

``` json
{
  "suspectId": "suspect_02"
}
```

The server returns the outcome and solution only after validating the
case, user, suspect, and completion state.

### 8.5 API behavior

-   Use appropriate HTTP status codes: `200`, `201`, `202`, `204`,
    `400`, `401`, `403`, `404`, `409`, `422`, `429`, and `500`.
-   Validate all inputs on the server.
-   Add pagination to case listing if needed; do not fetch unbounded
    collections.
-   Use consistent error codes.
-   Add rate limiting to auth and AI generation endpoints.
-   Use request IDs for traceable server logs.
-   Ensure CORS allows only configured frontend origins in production.

## 10. Security, privacy, and abuse prevention

-   Hash passwords using Argon2id or bcrypt with a suitable work factor.
-   Use HTTP-only, secure, same-site cookies for production
    sessions/tokens.
-   Protect state-changing cookie-authenticated endpoints against CSRF
    as appropriate.
-   Configure Helmet and restrictive CORS.
-   Rate-limit login, registration, generation, hints if needed, and
    accusation endpoints.
-   Validate and sanitize all user input.
-   Prevent NoSQL injection by validating query fields and avoiding
    direct use of untrusted objects in MongoDB filters.
-   Enforce ownership authorization on every case and progress endpoint.
-   Keep `GEMINI_API_KEY`, database URI, JWT/session secrets, and other
    secrets server-side.
-   Never commit `.env` files.
-   Provide `.env.example` with placeholder values only.
-   Do not use real personal data or real allegations in generated
    mysteries.
-   Clearly label all AI-generated cases and evidence as fictional.
-   Add a report/feedback mechanism only if separately scoped; MVP
    should not present generated content as verified fact.
-   Establish a reasonable data deletion behavior for account/case
    deletion before public launch.

## 11. Non-functional requirements

### 11.1 Performance

-   Initial page should render quickly on a typical broadband
    connection.
-   Lazy-load nonessential page sections and heavy assets.
-   Avoid loading every evidence artifact's full content if the case is
    large; fetch detail on demand if practical.
-   Show generation progress while waiting for Gemini.
-   Use database indexes for common owner/status queries.
-   Avoid unnecessary polling; use a sensible interval and stop polling
    when generation finishes or fails.

### 11.2 Reliability

-   Gemini failures must not crash the API process.
-   Database connection failures must produce controlled errors.
-   Failed generation must be recoverable through retry.
-   Prevent partial cases from appearing playable.
-   Use centralized error handling and structured logs.
-   Do not leak private solution data in logs or client payloads.

### 11.3 Maintainability

-   TypeScript strict mode enabled.
-   Shared API/data contracts where practical.
-   Runtime validation at trust boundaries.
-   Clear separation of routes, controllers, services, models, and UI
    features.
-   Avoid giant components and giant route/controller files.
-   Document non-obvious business rules.
-   Keep `SPEC.md` updated as approved requirements evolve.

### 11.4 Compatibility

-   Support current stable versions of Chrome, Edge, Firefox, and
    Safari.
-   Support current mobile browsers.

## 13. Testing strategy

### 13.1 Unit tests

Cover: - Scenario input validation. - Gemini response parsing. -
Generated mystery schema validation. - Semantic invariants: culprit
reference, evidence references, hint order, unique IDs, suspect count,
evidence count. - Spoiler filtering/public DTO serialization. - Hint
progression and no-skipping rules. - Accusation evaluation. - Ownership
authorization helpers.

### 13.2 API integration tests

Cover: - Registration, login, logout, and current-user endpoint. -
Protected route rejection without authentication. - User A cannot access
User B's case or progress. - Case creation and generation status. -
Invalid Gemini response is rejected and case is not marked ready. -
Public case response does not contain private solution fields. -
Progress update accepts valid evidence IDs and rejects invalid IDs. -
Hint endpoint reveals only the next hint. - Accusation rejects unknown
suspect IDs. - Correct and incorrect accusation outcomes. - Solution is
returned only after an authorized accusation/reveal. - Completed cases
cannot be submitted repeatedly.

Use a mocked Gemini service in automated tests. Do not require a live
Gemini API key for the normal test suite.

### 13.3 End-to-end smoke test

A Playwright happy-path test should:

1.  Register or log in as a test user.
2.  Create a mystery using a deterministic mocked AI response.
3.  Wait for case status `ready`.
4.  Open the case.
5.  Inspect a suspect and evidence artifact.
6.  Request a hint.
7.  Submit an accusation.
8.  Verify the outcome and solution explanation.
9.  Verify the case appears completed in the dashboard.

### 13.4 Manual acceptance checks

-   Test desktop and mobile layouts.
-   Test slow network and Gemini failure states.
-   Test invalid and very long scenario input.
-   Test refresh during generation and during investigation.
-   Confirm no spoilers appear in browser network responses before
    accusation.
-   Confirm user data isolation between accounts.

## 16. Required live demonstration scenario

The deployed application must demonstrate one complete, repeatable
mystery.

Suggested demo premise:

> During a private preview at a small city art gallery, a valuable
> miniature painting disappears between 8:00 PM and 8:30 PM. Four people
> were present: the gallery manager, a visiting collector, a security
> guard, and the restoration assistant. Their statements, messages, and
> camera logs contain inconsistencies. Determine who took the painting
> and how.

The AI-generated case should provide: - A briefing and incident
timeline. - 3--6 suspects. - Fictional chat messages. - At least one
CCTV log. - At least one document or witness statement. - At least one
photo description. - Three progressive hints. - A single canonical
culprit. - A final explanation that links the decisive evidence to the
culprit.

The demo operator must be able to create the premise from the UI,
investigate the resulting case, submit an accusation, and see the
solution on the deployed site. The generated culprit need not be
predetermined, but the generated case must pass validation and be
solvable.

## 17. Decisions and assumptions

These decisions define the MVP unless explicitly changed:

1.  **Single-player:** Each user investigates their own generated cases.
2.  **Creator is investigator:** The person who creates a case is the
    person who plays it in MVP.
3.  **Private cases:** Cases are private to their creator; public
    sharing is not included.
4.  **One final accusation:** The first final accusation reveals the
    solution and completes the attempt.
5.  **Hints:** Three pre-generated hints are stored with the case and
    revealed progressively.
6.  **AI-generated evidence:** Evidence content is generated by Gemini.
    Binary image/video generation is not required for MVP.
7.  **CCTV:** CCTV is a text-based fictional log/transcript.
8.  **Messaging:** Messaging evidence is a fictional chat transcript and
    is not connected to WhatsApp.
9.  **Solution secrecy:** Canonical solution is stored server-side and
    excluded from all pre-submission responses.
10. **Generation mode:** Use an asynchronous status/polling-compatible
    design even if the first implementation performs generation in a
    single request.
11. **Authentication:** Email/password authentication is sufficient for
    MVP.
12. **Deployment:** Use separate frontend/backend deployment if that
    simplifies hosting; exact providers are implementation choices.
13. **Case deletion:** User deletion of a case should delete its
    associated progress.
14. **No real allegations:** All cases and evidence are fictional and
    must be presented as such.

If a product decision changes, update this section and the affected
requirements/data contracts/API contracts before implementation.
